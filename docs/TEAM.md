## Как начать

Каждый клонирует этот репозиторий и переключается на свою ветку:

```bash
git clone https://github.com/BAITC-Hacks/hack-3ef0581f-setww.git
cd hack-3ef0581f-setww
git switch codex/research-ce
```

В последней команде участники 2/3 указывают свою ветку из таблицы.
Изменения в `main` вносим через небольшие PR с ссылкой на Issue.
После общего коммита обновляем ветки обычным merge/rebase, не перезаписывая чужую работу.

## Что каждый делает сам

- Формулирует гипотезу и записывает baseline/reference.
- Пишет собственный код и проверки forward/backward.
- Проверяет реальные градиенты и updates, затем запускает официальный T4 harness.
- Сохраняет commit, notebook/version, JSON и объяснение ограничений.
- Готовит короткое описание своей операции для README, видео и презентации.
- Делает review одного соседнего направления: R1 → R2 → R3 → R1.

## Как работать параллельно

1. Все используют [baseline #4](https://github.com/BAITC-Hacks/hack-3ef0581f-setww/issues/4), одинаковые зависимости и неизменённую задачу.
2. R1 и R2 заранее согласуют loss/metrics API. Пока R1 не готов, R2 использует reference CE.
3. R3 работает независимо от R1/R2; соединяется с ними после проверки своего результата.
4. Все изменения `solution/__init__.py` согласуются с одним интегратором — @kok-o.
   Никто не перетирает чужой `apply()`.
5. Микробенчи нужны для диагностики. Выбор по full-command time, nvidia-smi peak,
   качеству и обязательной доле собственных кернелов.

## Контрольные точки

| Когда | Что должно быть |

| Первые 30–60 минут совместной работы | Назначены R2/R3, подтверждён доступ Kaggle, запущен общий baseline |
| Через 2–3 часа | У каждого первый проверяемый прототип или конкретная причина остановки; R1/R2 согласовали API |
